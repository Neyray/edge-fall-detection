# 真实数据处理流程记录（初赛）

> 本文记录"从零拿到真实数据 → 训练 → 出指标 → 消融"的完整过程：挑了哪些数据、为什么这么挑、
> 每一步做了什么、结果如何。方便复现、扩量重跑、以及答辩时说清楚数据来源与方法。

---

## 0. 起点状态

- 代码框架已跑通，但**只有合成骨骼**（程序模拟的站立/跌倒），报告里的 accuracy=1.0 只能证明
  "链路能跑"，**不能当作真实检测效果**。
- 缺的就是一样东西：**真实数据 + 真实指标**。

## 1. 数据来源的选择与踩坑

### 1.1 选定数据集
- **Kaggle：`payutch/fall-video-dataset`**（CC0 许可，16 GB）。它同时提供原始视频和**逐帧
  COCO-17 骨骼关键点 CSV**（`Fall/Keypoints_CSV/`、`No_Fall/Keypoints_CSV/`），共 **6988 段**。

### 1.2 为什么最后用"骨骼 CSV"而不是视频
- 骨骼正是本项目**第二阶段（时序判别）的输入**。直接用数据集自带骨骼，可以
  **跳过下载 16 GB 视频、跳过跑 YOLO-Pose 抽骨骼**两步，快且省。
- 只打包骨骼 CSV 约 **297 MB**，视频那 ~15.9 GB 完全不用碰。

### 1.3 踩过的坑（为什么最初下载全失败）
1. **路径是照截图猜的、不存在**：数据集真实目录是 `Keypoints_CSV`，不是猜的 `Raw_Video/xxx.mp4`。
2. **Kaggle 单文件下载接口对该数据集整体失效**：`kaggle datasets download -f <单个文件>` 一律
   返回 404——连清单里确实存在的文件也 404。这是 Kaggle 已知问题，逐文件下载这条路走不通。

### 1.4 最终可行的下载办法（Kaggle 在线 Notebook）
关键：**Kaggle Notebook 跑在 Kaggle 云端**，那 16 GB 数据集已只读挂在云端 `/kaggle/input/`。
在 notebook 里用几行代码，在**云端**把所有 `.csv` 打包成一个 zip 写到 `/kaggle/working/`
（notebook 唯一可下载的输出区），本地只下这个 ~297 MB 的 zip。即"把计算搬到数据旁边，只带走结果"。

## 2. 挑了哪些数据、为什么这么挑

- **用哪一部分**：每类各取 **1500 段**（跌倒 1500 + 日常 1500），不是全用 6988 段。
  - 原因：全转会产生几万个窗口，CPU 训练慢且没必要；1500/类已足够训练 0.16M 的时序头。
- **类别均衡**：跌倒视频短（中位 ~56 帧）→ 窗口少；日常视频长 → 窗口多，窗口级天然 ~1:3.3 不均衡。
  训练时**下采样多数类到 1:1**，否则模型会偏向"日常"、压低跌倒召回。
- **按片段（clip）划分训练/验证**：同一段视频切出的多个窗口**整体**分到 train 或 val，绝不跨集。
  否则相邻窗口高度相似、同时出现在训练和验证 → 指标虚高（数据泄漏）。
- 一句话：**均衡 + 防泄漏 + 适量**，让指标可信。

最终划分：

| 划分 | 片段 | 窗口(均衡后) |
|---|---|---|
| 训练集 | 跌倒 1200 + 日常 1200 | 8122 |
| 验证集 | 跌倒 300 + 日常 300 | 2100 |

## 3. 处理流程（脚本与命令）

所有脚本在 `scripts/`，conda 环境 `yolo`。

| 步骤 | 脚本 | 作用 |
|---|---|---|
| ① 转换 | `csv2npz.py` | Kaggle 长表 CSV(`Frame,Keypoint,X,Y,Confidence`) → `(30,17,3)+label` 的 npz 窗口；逐帧按人体外接框归一化到 [-1,1]（与 `src/pose/extractor.py::normalize_keypoints` 对齐） |
| ② 选片+划分 | `prepare_real.py` | 每类选 N 段 → **按片段**划分 train/val（零泄漏）→ 各自转窗口 → **窗口级类别均衡**；输出验证片段清单 `reports/val_clips.txt` |
| ③ 训练 | `train_temporal.py` | 训练 Lite ST-GCN 时序头，存 `checkpoints/stgcn_fall.pt` |
| ④ 窗口级评测 | `evaluate_temporal.py` | 验证集窗口级 accuracy/recall/precision/F1 → `reports/eval_real.json` |
| ⑤ 事件级消融 | `ablation.py` | 对每段验证视频流式跑四种配置，判"整段是否报警"，出事件级指标 → `reports/ablation.json` |

复现命令：

```bash
conda activate yolo
cd ~/projects/edge-fall-detectioin

# 解压 keypoints_only.zip 到 data/kaggle_csv 后：
python scripts/prepare_real.py --src data/kaggle_csv --per-class 1500 \
    --train data/skeletons/train --val data/skeletons/val \
    --val-list reports/val_clips.txt --window 30 --stride 15
python scripts/train_temporal.py --data data/skeletons/train --val data/skeletons/val --epochs 18
python scripts/evaluate_temporal.py --data data/skeletons/val --ckpt checkpoints/stgcn_fall.pt --out reports/eval_real.json
python scripts/ablation.py --val-list reports/val_clips.txt --ckpt checkpoints/stgcn_fall.pt \
    --out reports/ablation.json --lie-sweep 0.15,0.2,0.3,0.4
```

## 4. 结果

**阶段2 时序头（窗口级）**：准确率 0.844 / 召回 0.840 / 精确 0.847 / F1 0.844

**事件级消融（以视频片段为单位）**：

| 配置 | 召回率 | 精确率 | 误报率 | F1 |
|---|---|---|---|---|
| 仅 ST-GCN | 0.997 | 0.634 | 0.573 | 0.775 |
| 仅 几何先验 | 0.843 | 0.797 | 0.213 | 0.820 |
| 融合（无状态机） | 0.987 | 0.822 | 0.213 | 0.897 |
| **融合 + 状态机（倒地≥0.15s）** | 0.886 | 0.858 | **0.147** | 0.872 |
| 融合 + 状态机（倒地≥0.4s） | 0.722 | 0.857 | **0.120** | 0.784 |

**结论**：几何融合把误报率 0.573→0.213（精确率 0.63→0.82）；状态机再降到 0.12–0.15，
提供"召回↔误报"可调旋钮。三级融合每个模块的价值都被独立验证。

## 5. 如实说明（答辩需交代）

- 本轮用的是数据集**自带骨骼**，**未接入 YOLO-Pose、未加红外/微光增强**，属于对
  **阶段2（时序头）+ 后处理（几何+状态机）** 的独立验证，而非完整端到端。
- 数据集片段是 ~2 秒的**跌倒事件短片**（跌倒片段中位 ~56 帧），故状态机"持续倒地"阈值按
  片段时长设为 0.15–0.4s；部署到长时监控流时应设回 1.5s，可在几乎不掉召回的情况下进一步降误报。
- 若要出完整端到端指标：把原始视频接入 `scripts/extract_skeletons.py`（跑 YOLO-Pose）再走同样流程即可。
